# Proposed enquiry persistence design

**PROPOSED — requires review before implementation.**

## Status, baseline, and scope

This document proposes storage for only manual enquiry creation, starting review, and qualification. It does not approve implementation, dependencies, database installation, credentials, or a change to business policy. The reviewed baseline is `ed24609a8f57158ea7d7eeb590a5005ce4a94081` (`test: close enquiry authorization audit gaps`). At design start, local `main` and `origin/main` were synchronized and the working tree was clean; origin was `https://github.com/bkaskd77-cmd/SoftterOs.git`.

The [workflow](ENQUIRY_TO_DRAFT_ITINERARY_WORKFLOW.md), [tenancy model](TENANCY_AND_ACCESS_MODEL.md), [security guardrails](SECURITY_AND_AI_GUARDRAILS.md), [blueprint](PROJECT_BLUEPRINT.md), and [repository instructions](../AGENTS.md) remain authoritative. Existing Go code is in-memory only. Every table, adapter, database role, integrity check, and integration test below is proposed, not implemented.

Preserve the modular monolith: the enquiry domain owns business invariants; platform authorization validates verified facts; the application coordinates one operation; a PostgreSQL adapter handles storage. Domain and authorization packages retain standard-library-only dependencies. No generic repository framework, event sourcing, separate service, queue, API, UI, AI integration, or new workflow operation is proposed.

| Command | Existing policy to preserve |
| --- | --- |
| Manual creation | Exact `enquiries.create`; owner and creator derive from verified context; `New`, unassigned, version 1. Historical travel dates remain valid. |
| Start review | Exact independent `enquiries.review`; authenticated human, same-organization membership and single-enquiry/action grant; `New` → `Under review`; atomically self-assign the acting membership; version 1 → 2. |
| Qualify | Exact independent `enquiries.qualify`; authenticated human, same-organization membership and grant; exact assigned membership; `Under review` → `Qualified`; retain assignment; version 2 → 3. |

Administrative status, possession of an ID, assignment alone, another membership, or the other capability supplies no authority. Skipping, repeating, cross-tenant transitions, reassignment, supervisor override, delegation, bulk operations, and AI-driven transitions remain denied. Qualification criteria and travel-date actionability are not newly defined here. Creation currently checks authenticated identity without the transition-specific `Human` test; storage must not silently change that policy or authorize an AI caller.

## Proposed relational model

Names below are logical names, not migration DDL. Use separate identity/access and enquiry storage namespaces owned by the corresponding modules. The application may coordinate them in one database transaction without turning authorization into a business-data repository.

| Table | Proposed key, fields, and relationships |
| --- | --- |
| `actors` | Global `actor_id` primary key, with only the minimal identity reference needed for attribution. No organization column, contact profile, password, credential, or assumption of one organization per person. Authentication and human attestation remain trusted-adapter responsibilities. |
| `organizations` | `organization_id` primary key; minimal ownership anchor only. No new organization type or operational-capability policy. |
| `memberships` | Primary key `(organization_id, membership_id)`; `actor_id` references `actors`; organization references `organizations`; active/revoked flags and nonempty validity interval. Add unique `(organization_id, membership_id, actor_id)` for composite attribution references. No uniqueness on actor alone or on `(actor_id, organization_id)`; several memberships must remain distinguishable. Identity and organization bindings are immutable. |
| `membership_enquiry_capabilities` | Primary key `(organization_id, membership_id, capability)`; composite membership foreign key. Only the three exact capability strings in this slice. These are resolved effective entitlements, not role labels. Missing rows deny. They do not explain or invent the upstream policy that permits their issuance. |
| `enquiry_transition_grants` | Primary key `(organization_id, grant_id)`; actor, membership, enquiry, exact review/qualify capability, active/revoked flags, validity start/end. Composite references bind the membership/actor and enquiry to the same organization. Add a unique full binding `(organization_id, grant_id, enquiry_id, actor_id, membership_id, capability)` for audit references. A grant's identity, subject, resource, and action binding cannot be repurposed; changed bindings require another grant. |
| `actor_authority_fences`, `organization_authority_fences` | One row per actor or organization, with its referenced key and positive authority revision. These coordinate reads with trusted policy/identity changes as described below. They are technical synchronization records, not capabilities. Missing fence rows deny. |
| `enquiries` | Primary key `(organization_id, enquiry_id)`; contact name/email, destination, traveller count, nullable travel start/end, state, creator actor/membership, creation instant, nullable assignee membership, version, last-change instant. Creator triple references the membership/actor binding; assignee pair references a membership in the owning organization. State and assignment occupy the same row. |
| `enquiry_events` | Primary key `(organization_id, event_id)`; enquiry foreign key; unique `(organization_id, enquiry_id, resulting_version)`. Immutable success facts and technical envelope described below. No enquiry input payload. |
| `enquiry_command_receipts` | Proposed duplicate/commit-recovery support, requiring approval: primary key `(organization_id, membership_id, request_key)`; actor/member binding, exact command, target enquiry where applicable, expected version, protected request fingerprint, event/resulting-version reference, completion instant. References include organization; the event link also binds the enquiry and version. A committed receipt represents a committed outcome, never merely an accepted request. |

Global identity does not confer global access. All tables except global actor anchors/fences are scoped by their organization key. One actor can act through multiple independent memberships, including memberships in different organizations; checks always select exactly one. No collaboration or traveller-access tables are added. Historical creator/assignee references remain valid when a membership is later revoked; referential existence must not imply present authorization.

Use opaque `text` IDs with the existing ASCII grammar (1–128 characters, alphanumeric first, then alphanumeric, hyphen, or underscore), exact case-sensitive comparison, and deterministic collation for keys. Recommend server-generated random identifiers encoded within that grammar; approve the generator separately. Tenant-local composite uniqueness is sufficient: every lookup includes organization even if generated IDs happen to be globally unique. No caller-selected ownership or global lookup fallback is permitted.

Proposed constraints:

- Required fields are `NOT NULL`; optional date/assignee fields use explicit nullability, not empty or magic sentinel IDs. Foreign keys include tenant identity on both sides; creator and audit actor/member references use the full membership binding. No cascading deletion of business or audit evidence; use restrictive references until an approved retention design exists.
- `enquiries` accepts only the reachable combinations `New`/unassigned/version 1, `Under review`/assigned/version 2, and `Qualified`/assigned/version 3. Use `bigint` with those bounds and checked conversion to Go `uint64`. This models the current closed slice, not a permanent rule for future editing: another authorized operation requires revisiting the constraint. Reject unknown states/versions rather than guessing a forward-compatible interpretation.
- Preserve creator, owner, input, and creation instant across these two transitions. Runtime updates have column privileges only for state, assignee, version, and last-change instant. A narrow integrity trigger should reject skipped/repeated updates, assignment replacement, or version jumps even if an adapter issues incorrect DML. Go still decides authorization; database structural checks do not grant capabilities.
- Travel dates use `date`, both absent or both present, year 1–9999, start ≤ end. Reject infinity and values outside the Go range. Decode back to exact `YYYY-MM-DD`; never compare with action time. Validate the caller's original format in Go before binding a typed date: PostgreSQL's date parser is not a replacement for that validation.
- Mirror simple input bounds (name 120 characters, destination 200, email 254 bytes, traveller count 1–99). Reuse the complete Go checks for UTF-8, trimming, controls, email syntax, and date invariants on write and reconstruction; database length constraints alone are insufficient.
- Instants use finite `timestamptz`, valid nonzero Go range, with last change ≥ creation and nonempty inclusive-start/exclusive-end membership/grant intervals. PostgreSQL stores timestamp precision at microseconds; **propose** a microsecond persistence contract and reject higher-precision authority bounds rather than silently round or extend validity. Use a single representable action instant for domain and audit. Approval is required for this precision contract; existing nanosecond unit tests and in-memory semantics remain unchanged. PostgreSQL dates have no time of day and `timestamptz` preserves an instant, not an organization timezone. [PostgreSQL date/time types](https://www.postgresql.org/docs/18/datatype-datetime.html)

Use the primary/unique indexes above for command lookups and event uniqueness. Add indexes for referencing creator/assignee membership columns, grant-to-enquiry/member columns, receipt-to-event columns, and `memberships(actor_id, organization_id, membership_id)` where not already covered by a leftmost index prefix. The event version index also orders an enquiry's three events. Do not add speculative contact, search, analytics, or queue indexes. PostgreSQL does not automatically index the referencing side of a foreign key; composite foreign keys and unique targets enforce the proposed relationships. Cross-row integrity requires foreign keys or triggers, not a `CHECK` that queries other rows. [PostgreSQL constraints](https://www.postgresql.org/docs/18/ddl-constraints.html)

## Tenant isolation, roles, and pooled connections

Every adapter query, join, update, and receipt lookup must include the verified owning organization. Enquiry identifiers from a command are selectors only; the loaded row supplies authoritative ownership and state. Never inspect another tenant to explain a failed lookup. A missing, inaccessible, or foreign-tenant resource has the same safe external result.

Enable and force row-level security (RLS) on tenant tables, including memberships, capabilities, grants, fences, audit events, and receipts. Restrict the organization anchor to the selected organization too. Explicit `USING` and `WITH CHECK` policies bind ownership to verified transaction context; missing, empty, malformed, or inconsistent context denies. No policy permits changing ownership. Keep policies simple and do not treat them as a substitute for action/assignment checks. PostgreSQL RLS defaults to denial when enabled without a policy; table owners ordinarily bypass it, and superuser/`BYPASSRLS` roles bypass it even with forcing. Integrity checks bypass RLS and can reveal existence through raw errors, so sanitize constraint failures. RLS does not cover `TRUNCATE`. [PostgreSQL row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)

| Database role boundary | Proposed privileges and exclusions |
| --- | --- |
| Runtime application | Non-owner login; `NOSUPERUSER`, `NOBYPASSRLS`, no role/database creation, no migration-role membership or `SET ROLE` route to it. Tenant-scoped necessary reads; enquiry insert and limited update; event insert only; narrow receipt writes. No delete/truncate, schema creation, policy changes, or authority-table writes. Audit reads are limited to internal consistency/recovery, not a user audit-browser permission. |
| Migration/owner | Separate credentials and execution path, never in the runtime pool. Own schema and reviewed migrations; capable of changing protections, therefore privileged and outside RLS tamper-resistance claims. |
| Trusted authority writer | Separate restricted path for synthetic fixtures initially and a later approved policy adapter. May update authority facts through the locking protocol; no enquiry or success-event mutation. This is a technical boundary, not approval of who may administer grants. |
| Fence-lock helper owner | Non-login, non-superuser, non-owner of business/authority tables, no `BYPASSRLS`; only the fence permissions needed by the narrowly scoped helper below. Runtime cannot assume this role. |

Provision explicit grants/default privileges so `PUBLIC`, inherited roles, or writable schemas cannot defeat this matrix. Global actor anchors/fences are not a browsable directory: scope their runtime access to the trusted authenticated actor, with identity-specific RLS or the narrow helper. An enquiry's historical actors can remain referenced without exposing their identity records. [PostgreSQL role attributes](https://www.postgresql.org/docs/18/sql-createrole.html)

For each operation, begin one transaction on one acquired connection. After trusted identity/organization selection, bind tenant and actor context with parameterized `set_config(..., true)` inside that transaction. Validate the bound values against the trusted adapter's values; membership/capabilities are loaded and checked, not inferred from settings. Never use session-level tenant settings or connection-string tenant defaults. All command queries use the same transaction handle, never pool-level query methods that could select another connection. Transaction-local settings end at commit/rollback; rolling back to a savepoint can undo settings, so do not introduce savepoint retries around context setup. [Configuration functions](https://www.postgresql.org/docs/18/functions-admin.html), [SET scope](https://www.postgresql.org/docs/18/sql-set.html)

Initialize pooled connections with no tenant context, detect/reject residual session context on acquisition, and release only after successful cleanup. Use bounded rollback cleanup even after request cancellation; discard a connection if cleanup or state verification fails. Test tenant A → tenant B → no-context reuse after success, errors, cancellation, and panic cleanup. A configurable tenant setting is not authentication: a compromised runtime credential or arbitrary SQL execution could set another tenant value. This proposal protects against omitted filters and normal adapter mistakes; it does not claim RLS defeats compromise of the trusted context-setting tier. Parameterized statements, restricted credentials, and an approved external trust boundary remain mandatory.

## Validated domain reconstruction

The current private `Enquiry` has no storage constructor and no accessor for `lastChangedAt`. Propose a domain-owned, validated storage snapshot/restore boundary in a later implementation, plus a detached snapshot exporter. This is a required code change for persistence, not part of this documentation task. Do not export mutable fields, use reflection/unsafe writes, deserialize a client DTO into domain state, or replay `New` with fabricated authorization to impersonate historical creation.

The adapter decodes a typed storage record with explicit null handling. The domain restore function validates every ID, original input, finite timestamp, owner/creator/member binding evidence, reachable state/version/assignment combination, and last-change ordering before constructing a private value. Validate `New` with last-change equal to creation; validate later states against matching event/version evidence and the original creator facts. Cross-table bindings and the complete event chain are checked in the same transaction by the adapter/integrity constraints; a domain value alone cannot prove that those references exist. Return no partial value on any mismatch. Treat unknown schema/state, truncated data, malformed records, or absent audit evidence as safe integrity failures requiring investigation, never auto-repair.

Restore validates history, not current permission: a revoked creator membership does not invalidate an otherwise legitimate historical enquiry. A reconstructed record never creates an authorization proof. Current action authority must still be obtained separately. Storage snapshots and restore entry points are internal trusted-adapter interfaces; future transport/AI code must not call them or supply their data. Tests must prove round-trip preservation of all private state and detached results, including `lastChangedAt`, historical travel dates, creator facts, and multiple distinct memberships.

## Current authority and concurrent revocation

**Recommendation requiring approval:** keep the current membership, effective enquiry capabilities, and direct transition-grant authority in the same PostgreSQL transaction domain as enquiry writes. A trusted identity adapter supplies authenticated actor and human attestation; the local test harness supplies synthetic attestations only. The tables are authoritative current policy records for the experiment, not a periodically refreshed cache claimed to be current. Policy derivation, organization operational rules, purpose/field restrictions, and grant-issuer eligibility remain undecided; fixtures must label these as assumed pre-resolved facts, not an implemented policy engine.

Coordinate policy changes using the fence rows:

1. A business transaction locks its actor fence, then organization fence, in shared mode, before reading authority. Retain locks until transaction end. Load membership/capability/grant facts after obtaining locks and revalidate identity attestation through the coordinated identity adapter; if any expected fence or authority record is absent, deny. For synthetic actor-revocation tests, the harness changes its identity attestation under the exclusive actor fence and the command rereads that fixture after obtaining its shared lock. This is a test double, not a session verifier or a production revocation ledger. An old `authz.Context`, its timestamp, or a matching cached revision is not a substitute for these reads.
2. Every trusted writer changing organization policy, membership, entitlement, grant, or upstream restriction takes an exclusive organization fence lock **before** modifying facts, increments its revision, and commits the change atomically. Actor/session revocation affecting all memberships must coordinate on the actor fence. Writers affecting both take actor then organization locks, with deterministic ordering for multiple keys. Never upgrade a business shared lock into a policy-writing operation.
3. A revocation committed first is observed and denies the operation. If the business transaction acquired its shared lock first, the writer waits; the command either commits before the revocation or rolls back. Once revocation is acknowledged committed, later commands cannot use pre-revocation facts. This ordering for in-flight operations needs explicit approval; it does not cancel an operation already ordered before revocation. A revision number documents the authority basis but provides no synchronization without the writer protocol.

PostgreSQL `FOR SHARE` blocks conflicting updates/exclusive row locks while permitting other shared readers. `FOR KEY SHARE` is insufficient for changes to non-key policy fields. Holding the organization fence trades some policy-update latency for an explicit, testable ordering without serializing all independent business reads. All writers must participate; uncoordinated external updates invalidate the guarantee. [PostgreSQL locking](https://www.postgresql.org/docs/18/explicit-locking.html)

Row-locking `SELECT` also requires an `UPDATE` privilege, so do not solve this by granting the runtime arbitrary authority writes. Propose one lock-only `SECURITY DEFINER` helper owned by the limited fence-lock role: validate exact actor/organization context, acquire the shared fence locks, return their revisions, and perform no authority mutation. Use fully qualified objects, a fixed trusted search path with temporary schema last, no dynamic SQL, no `PUBLIC` execution, and explicit runtime execute permission. Its owner remains subject to the relevant RLS. Review and adversarially test this small privileged interface before using it. [SELECT privileges](https://www.postgresql.org/docs/18/sql-select.html), [safe security-definer functions](https://www.postgresql.org/docs/18/sql-createfunction.html)

External credential/session revocation is a distinct boundary. A future identity/policy provider must either participate through a coordinated authoritative local revocation ledger with defined acknowledgement semantics, or provide another reviewed freshness/commit protocol. Polling, cached tokens, a network check just before `COMMIT`, and `SERIALIZABLE` on the local database alone cannot prevent an external revocation racing that commit. Until that contract is approved, use synthetic identities only and do not accept untrusted requests. No stale fallback is allowed when the required authority source is unavailable. Do not create session/credential storage or pick an identity provider in this slice.

## Transaction ownership and command ordering

The application owns one unit of work; infrastructure implements its transaction-bound operations. Repositories must not commit independently. Domain and authorization types must not import driver transactions. The current application constructors can receive a trusted operation clock, but their existing success values are only candidates until the persistence coordinator commits.

Recommend PostgreSQL `READ COMMITTED` with explicit authority/enquiry locks, conditional version writes, and the unique constraints above. Each command operates on one enquiry; no multi-resource predicate rule currently needs a broader isolation design. `READ COMMITTED` reads can see new committed data on successive statements; locking reads wait and return the updated row. Locks and conditions, not the isolation-level name alone, establish this proposal's guarantees. Reconsider `SERIALIZABLE` if a later approved rule depends on a set of resources; it still requires retry handling and does not verify external authority. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html)

Proposed ordering for a new command:

1. Trusted entry code verifies identity and explicit organization selection; reject missing/malformed context before business reads. Treat request key, enquiry selector, expected version, and creation input as untrusted. Do not accept serialized contexts, grants, ownership, actor, assignee, or clocks. Start the transaction, set scoped context, take authority locks, and load current facts. Perform membership/action/scope checks before accessing contact data. For transitions, a current grant must bind the selector to this tenant/action; there is no unrestricted enquiry lookup. For creation, perform current preflight creation authorization and existing input validation before fingerprinting or reserving a receipt. Preflight authorization does not replace the fresh post-wait check below.
2. If receipt support is approved, reserve the scoped request key under its unique constraint using the current actor/membership and protected canonical fingerprint. Reservation is transaction-local and rolls back on failure; never commit a pending receipt. Resolve a competing receipt before locking an enquiry, in the same lock order for every command. Recover an existing committed result only through the separately approved protocol below.
3. For review/qualification, load `(verified organization, enquiry ID)` with a row lock. Fetch only the fields needed by the command. No row means a safe unavailable/unauthorized result. Verify its owner against active organization; reconstruct it through validation. For creation there is no existing row to load or assign.
4. After all potentially blocking locks, obtain a fresh trusted action instant. Recommend the database's `clock_timestamp()` for the future adapter, injected into the existing deterministic Go boundary. `now()`/`CURRENT_TIMESTAMP` represents transaction start and can be stale after waiting. Check inclusive/exclusive validity and current human/grant facts using this action instant. Never use travel dates, a client clock, or a previously issued proof. [PostgreSQL current-time functions](https://www.postgresql.org/docs/18/functions-datetime.html)
5. Run the exact Go authorization against the authoritative enquiry identifiers before exposing state/version diagnostics. Compare command expected version with the stored version, then invoke the existing domain transition. Creation retains authorization-before-input/ID-generation ordering and derives ownership from fresh context. Generate identifiers inside this authorized attempt; rollback may leave unused IDs but no business record. Any domain denial returns no persisted outcome.
6. Insert a new enquiry or conditionally update exactly one row constrained by tenant, ID, expected stored version, and appropriate prior state/assignment. Save state, assignment, version, and last-change instant together. Zero affected rows is a conflict/unavailable result, never a reason to overwrite or silently retry against a newer version. Only the resulting immutable domain value supplies changed fields.
7. Insert the matching success event and complete the receipt in the same transaction. Validate cross-record integrity at transaction end: exactly one event per resulting version, a contiguous history through that version (one, two, or three events respectively), and matching state/assignment/creator/time facts. Propose narrowly scoped deferred constraint triggers for this consistency, including rejection of a new version without an event, an event without its matching change, or an incomplete receipt at commit. They enforce structural integrity, not duplicate the authorization engine. Any event, receipt, constraint, or storage failure rolls back all writes. PostgreSQL supports transaction-end firing of deferred constraint triggers. [PostgreSQL constraint triggers](https://www.postgresql.org/docs/18/sql-createtrigger.html)
8. Immediately before commit, recheck time-based validity from the locked facts against a fresh server instant; if expiry occurred while doing database work, roll back rather than use the old instant as freshness. Retain the original action instant in domain/audit facts. This extra conservative expiry check is a proposed persistence behavior requiring approval. The authorization ordering point remains the action check under locks; neither a final clock check nor this design guarantees validity at an unknowable future commit/response wall-clock instant. Do no network/user/AI work while locks are held.
9. Commit, then return success. Do not emit an external success event or publish the candidate result before commit. A failed or ambiguous commit returns no claimed success; reconcile as below. Require durable PostgreSQL tables and normal synchronous commit/WAL durability settings for any durability claim, not unlogged tables or asynchronous acknowledgement. This does not promise backup, failover, or disaster recovery. [PostgreSQL asynchronous commit tradeoff](https://www.postgresql.org/docs/18/wal-async-commit.html)

## Concurrency, duplicate requests, retries, and errors

Two authorized reviewers can concurrently claim the same `New` enquiry, but only one may commit version 2 and self-assignment. The loser observes the committed version/state after waiting and fails; its receipt reservation and candidate event roll back. A lock timeout must not skip the row or choose an alternative assignee. Qualification rechecks the exact stored membership, not merely the same actor or a different membership belonging to that person. Stale expected versions are never refreshed automatically. A new request repeating an already completed transition remains invalid.

**Proposed command-recovery semantics require approval.** Recommend a scoped idempotency key plus receipt for all three commands, especially creation, which otherwise has no expected-version duplicate guard. The same key must identify the same actor, membership, command, selector, expected version, and exact validated creation input. Use a versioned keyed fingerprint to compare private input without storing it twice; no plain hash advertised as anonymization. Approve canonicalization, key management, and receipt lifetime before real data. Synthetic tests can use an ephemeral test key. The request key is never an authorization secret or resource ID.

A duplicate key with different command facts fails safely. Matching concurrent submissions converge on one committed event/receipt through uniqueness; after a winner rolls back, a new fully authorized attempt can proceed. On a matching committed receipt, do not rerun the domain transition, update timestamps, create another audit event, or return a later mutable enquiry as the old result. Recommend returning only a committed-command acknowledgement (tenant-scoped resource/event IDs, action, resulting version, original instant), expressly a recovered prior outcome. This is different from permitting repeated transitions and must be approved as a command contract. Do not infer business duplicates from contact email or similar input; that is deferred product policy.

Recovery must reverify identity, selected organization, same membership/actor, current exact capability, and resource/action grant where required. It cannot use the old receipt's successful authorization as present permission. A now-revoked actor/member/grant receives no receipt details; an internal authorized reconciliation path may still establish whether a commit occurred. Creation/transition authority does not imply a general read/audit capability. Approval must explicitly bound command acknowledgement access; until then, no user-facing receipt read path or replay-success behavior is authorized. No cached full enquiry/contact response is proposed.

On a lost connection or timeout during `COMMIT`, the outcome may be unknown: do not claim rollback and do not resubmit with a new key. Use a fresh connection to the authoritative primary and the same scoped key under fresh authorization. If the original transaction is unresolved, wait within bounded limits or report outcome unknown. A missing receipt from one read is not proof that an in-flight transaction cannot later commit; a retry with the same key must serialize with it via uniqueness. A persisted receipt links to the matching committed event. If safe resolution is unavailable, preserve the uncertainty instead of guessing. This is at-most-one committed command per retained key, not a universal exactly-once delivery guarantee.

Retry only a complete transaction known to have aborted, with fresh authority/time/row loading, bounded attempts, and the original expected version/key. SQLSTATE `40001` and appropriate deadlock `40P01` are candidates; do not automatically retry denials, stale versions, malformed records, arbitrary uniqueness violations, or ambiguous commits. PostgreSQL requires retrying the whole transaction, not just the failing statement. [PostgreSQL serialization failure handling](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)

Translate infrastructure errors into safe categories: unauthorized/unavailable resource, invalid input/transition, version conflict, temporary storage failure, integrity failure, and outcome unknown. Preserve existing domain sentinels internally. Never expose SQL, constraint values, connection strings, contacts, authority details, or another tenant's existence. Log a safe correlation ID/reason category under restricted diagnostics. Authorization must precede informative state/version errors. A denial or rollback leaves the entire enquiry, assignment, receipt, and success-event set unchanged; separate minimized denial telemetry is not a success event and must not be falsely rolled into the aborted transaction as durable evidence.

## Audit protection and minimized data

Store typed success events, not arbitrary JSON or text. Common fields: event ID, command/correlation ID, action, fixed success outcome/reason category, owning/active organization, enquiry, actor, membership, exact capability, action instant, resulting version, and relevant authority revisions. Both organizations must match for this slice. Creation records `enquiry.created`, `enquiries.create`, initial `New`, version 1, and no prior state/assignee or transition-grant ID; do not invent a grant for creation. Enrich the existing detached creation facts only with trusted envelope values and known initial-state facts.

Transitions retain every existing `TransitionAudit` field: previous/new states, previous/resulting versions, previous/resulting assignee, actor/member/grant/capability, organizations, enquiry, action, and instant. Bind transition grant evidence with the full immutable grant tuple, and enforce the event's actor/member/organization references. Event IDs/correlation IDs are generated or strictly validated technical values, never free-text excuses or credentials. Audit events do not contain contact names/emails, destinations, travel dates, passports, medical/payment information, tokens, request bodies, or AI prompts.

Constrain the event shape by exact action: creation has absent prior state/version/assignee and no transition grant; review has `New` → `Under review`, versions 1 → 2, no prior assignee, and the acting membership as new assignee; qualification has `Under review` → `Qualified`, versions 2 → 3, and the same acting membership in both assignee fields. Transition grant/binding fields must be non-null, so nullable foreign-key components cannot bypass their checks. Receipt completion requires an event and resource/resulting-version binding even for creation; a pending nullable reservation is never a valid committed receipt.

Runtime may append valid events in the command transaction but cannot update/delete them. The integrity checks above catch mismatched/omitted events; they do not prove that a compromised trusted runtime told the truth about authorization. Owners, privileged migrations, and database administrators remain powerful. Before real data, approve audit-reader authority, denied-action telemetry, operational access review, tamper detection/protection appropriate to the threat model, and backup/restore verification. No hash chain, external log service, retention period, or compliance claim is silently required or implemented here. Deletion/anonymization, legal holds, and receipt/key lifetime must be designed together without undermining audit accountability or keeping personal data indefinitely.

## Driver and narrowly scoped dependency proposal

Recommend `github.com/jackc/pgx/v5` with `pgxpool` in the PostgreSQL infrastructure adapter only. The upstream project recommends its native interface when PostgreSQL is the sole target and no library requires `database/sql`; `pgx/v5/stdlib` remains a reasonable alternative if standard `database/sql` interfaces become useful. The native option offers explicit PostgreSQL transaction/error/type handling; the alternative adds abstraction without removing the external driver requirement. Choose one pool, not both layered together. [Upstream pgx guidance](https://github.com/jackc/pgx)

Propose an exception limited to a reviewed, pinned pgx v5 release and its necessary transitive runtime modules. Domain, authorization, and their tests stay standard-library-only; application ports expose project/standard-library types. No ORM, migration framework, query generator, mocking framework, or unrelated package is included in this exception. The inspected upstream v5.10.0 module declares additional modules, so the exception cannot truthfully mean one dependency with no transitive code. Inventory the actual build graph, versions, licenses, and advisories before approval; distinguish runtime from upstream test dependencies. Select the then-supported patch after verification with required Go 1.27.3 and the approved PostgreSQL version. No dependency policy, `go.mod`, or `go.sum` changes are authorized by this proposal. [Upstream versioned module manifest](https://github.com/jackc/pgx/blob/v5.10.0/go.mod)

Use parameterized queries and explicit transaction methods. In the inspected pgxpool implementation, canceling the context used to begin a transaction does not automatically roll it back; implementation must always finalize it and safely release/discard its connection. ## Proposed local integration-test plan

After separate implementation/environment approval, use only a local disposable database, synthetic identities/grants, and contacts at reserved example domains. Verify an explicit local target and disposable database marker before setup or cleanup; never run fixtures against a shared/customer database. Use migration and runtime roles separately. Allocate independent test databases or isolated fixtures for concurrent tests; use barriers and actual separate connections rather than timing-only sleeps. Drop only the verified disposable resources after tests, including failed runs. No database or test environment is created by this task.

| Area | Required evidence before considering the adapter complete |
| --- | --- |
| Round trips | Create, review, qualify; exact input, creator, owner, assignee, version, last-change and audit values after reload; multiple actors/memberships and one actor in multiple organizations. Historical dates, leap days, complete/ordered ranges, limits, null handling, and precision boundaries remain correct. |
| Tenant isolation | Run as the real runtime role: deliberately omit a query filter; absent/wrong/empty context; guessed IDs; joins; cross-tenant creator/assignee/grant/event/receipt references; immutable ownership. Include the isolated org-2 active/member versus org-1 grant/enquiry case. No cross-tenant data or raw constraint errors escape. |
| Roles and pooling | Runtime cannot become owner, bypass RLS, change policies/authority, update/delete audits, truncate, or create shadow objects. Verify helper scope/search-path protection. Reuse one connection across tenants and no-context operations after commit, rollback, cancellation, errors, and cleanup failure. |
| Competition and stale writes | Simultaneous review claims by different memberships: exactly one state/assignment/event commits, loser changes nothing. Qualification by another membership of the same actor fails. Stale/zero versions, direct/repeated/invalid transitions, and concurrent qualifications produce no duplicate events. |
| Authority freshness | Revoke membership, remove effective capability, revoke/change grant status, or invalidate actor authority while another connection waits. Exercise both fence acquisition orders; revocation-first denies, command-first finishes or rolls back before revocation acknowledges. Test absent fences, source failure, and newly built context using changed facts. |
| Expiry | Exact inclusive start/exclusive expiry for both membership and grant; expiry while waiting for the enquiry lock; expiry before final commit check; a stale pre-wait timestamp must not authorize. Test precision contract rejection without extending a validity interval. |
| Corrupt storage | Constraint-level rejection of cross-tenant and malformed rows; isolated privileged fixture injection or decoded-record tests for conditions beyond SQL checks. Unknown states, wrong versions, invalid text/date/time, wrong identity binding, absent/mismatched audit chain, and last-change-before-creation fail restoration safely. Never relax the runtime role to create these fixtures. |
| Atomic failure | Force event insert failure after the candidate enquiry write; independently observe complete rollback of creation or transition, assignment, version, timestamp, receipt, and all events. Also fail receipt completion and deferred integrity checks. No success result escapes. |
| Duplicate and uncertain outcomes | Same key/same facts concurrently commits once; changed facts/key misuse fails; independent keys do not merge enquiries. Abort-before-commit can retry; drop acknowledgement after commit recovers only the prior minimal outcome under current authority; unresolved commit is not treated as rollback. Revoked recovery callers get no details. |

Keep the existing unit/authorization tests, race tests, vet, formatting, and diff checks. Database tests supplement rather than replace the mutation-proven authorization boundaries. Successful integration tests would validate a local synthetic-data adapter, not external identity verification, production operations, or all future workflows.

## Decisions and approval gates

All recommendations remain proposals. No additional business capability, qualification threshold, organization policy, grant-administration authority, retention period, vendor, or traffic target is decided here.

| Before local synthetic-data implementation | Recommendation and tradeoff requiring approval |
| --- | --- |
| Implementation boundary | Authorize a later code/schema task limited to these commands, validated restore/export, transaction coordinator, structural integrity checks, and integration tests. Preserve existing policy and module direction. |
| Environment and driver exception | Approve local disposable PostgreSQL setup method/version and pinned pgx dependency graph. No installation or dependency change until then. |
| Keys and representation | Approve composite tenant keys, generated ID format, the closed state/version model, finite microsecond persistence contract, and snapshot validation. Rejecting unsupported precision is safer than silent rounding but narrows accepted storage facts. |
| Authority experiment | Approve co-located effective facts, synthetic identity attestation, actor/organization fence protocol, and limited lock helper. This makes revocation ordering testable but requires every authority writer to cooperate; it does not implement policy derivation. |
| In-flight authorization and expiry | Approve command-before-revocation ordering under locks and the final conservative expiry check. If revocation must cancel already in-flight operations or validity must hold at a different ordering point, resolve that requirement before coding. |
| Duplicate/commit recovery | Approve scoped receipts, canonical fingerprint, minimal recovered acknowledgement and its access checks. Alternatively defer automatic recovery and explicitly return outcome unknown; blindly retrying creation is not acceptable. No receipt response is an implicit general read permission. |

Before accepting **untrusted requests**, separately approve and implement verified identity/session construction, authoritative policy/operational-capability and grant derivation/administration, coordinated revocation/freshness contract, server-side request/response and field controls, command-recovery authorization, scoped reads, bounded resource use, and safe denial telemetry. Synthetic fixtures cannot substitute for these. The existing human-only transition rule and AI prohibition remain mandatory; no AI integration is implied.

Before storing **real customer data**, additionally approve purposes/access for stored fields and audit readers; retention/deletion/anonymization and receipt lifetime; credential/key handling, encryption/residency requirements as applicable; privileged access controls; durable audit protection; backup/restore and incident procedures. Do not choose periods, hosting, compliance obligations, or legal-hold rules by inference. Qualification evidence and travel-date actionability need product decisions before a later workflow automates or relies on them; persistence must merely preserve the existing authorized human decisions.

Local implementation approval would not authorize external requests, customer data, deployment, or any of the deferred workflow. This document and its workflow reference do not change the current implementation boundary.
